# Pipeline Generation Policy and Integration Contract

**Status: proposed policy for owner review. Not approved, implemented, or enforced.**

This document records the Phase 88 contract proposal for pipeline run accounting and generation consistency. It does not connect `pipeline_generation_store.py` to production. The Phase 66 Windows filesystem security rejection remains in force: evidence reading is blocked, collection publication is closed, `AUTO_SUBMIT` must remain false, and browser auditing must remain disabled. A passing offline test suite is not filesystem-security approval.

## 1. Evidence categories

### Verified repository facts

- `pipeline_generation_store.py` defines schema version 1 for manifests and pointers, stages `job_details` and `job_analyzer`, and statuses `IN_PROGRESS`, `COMPLETE`, `EMPTY`, `PARTIAL`, and `FAILED`. It validates schema, accounting, output fingerprints, and analyzer input-generation references. It reads artifacts by ordinary path operations and explicitly does not establish trusted-root containment, reparse-point resistance, safe path replacement, or crash durability.
- The helper has no production writer, pointer publisher, locking protocol, or recovery workflow. Its tests exercise the helper in isolation; the helper is not imported by the production pipeline.
- `job_search.py` names `jobs.csv` as its output, but `publish_collection()` currently returns `False` for all outcomes (`job_search.py:376–395`). `job_scraper.py` returns scraped rows and reports collection completeness as unknown; the inspected source does not establish it as an authoritative publisher.
- `job_details.py` reads fixed-path `jobs.csv`, writes `data/job_details.csv` and `data/job_details_diagnostics.json` sequentially through a single-file replacement helper. A valid zero-row input returns without replacing prior outputs. Missing-link records are currently skipped without an output row or diagnostic. Per-record extraction exceptions produce a row and diagnostic; the row may have a blank description.
- `job_analyzer.py` reads fixed-path `data/job_details.csv` and writes `data/job_analysis.csv`. A valid empty input returns without replacing a previous analysis file. Inadequate descriptions can produce `INSUFFICIENT_DATA` and an ineligible analysis row. `output_files.py` replaces one file at a time; it does not make multiple outputs transactional.
- `easy_apply.py` reads fixed jobs/details/analysis paths. Its freshness guard compares file timestamps and job identities/multiplicity; it does not bind parsed bytes to a generation ID or content hash. Candidate selection applies downstream eligibility filters. Application tracker/history are persistent files separate from generated analysis.
- `application_tracker.py` defines a fixed analysis input path, but the tracker itself is persistent editable application state. `easy_apply.py` also reads and updates tracker/history state.
- `COLLECTION_EVIDENCE_POLICY.md` keeps collection publication closed. `WINDOWS_FILESYSTEM_SECURITY_REVIEW_PACKAGE.md` records the Phase 66 rejection and current evidence-reading hold.

These facts describe inspected source, not runtime execution or external consumers.

### Proposed choices in this contract

The policy below is recommended for review. Each item marked **Owner approval required** remains a product decision; it is not made binding by this document.

## 2. Source of truth and run identity

**Recommendation:** Treat the exact byte snapshot of the `jobs.csv` consumed by one `job_details` run as that run's source of truth. Parse and process that same snapshot; fingerprint its raw bytes with SHA-256 and record the source byte size. Do not fingerprint one read and then parse a second path read. Each parsed data row is a distinct source occurrence, including duplicate job identities.

The repository does not establish which producer is authoritative. The collection writer is currently closed, and the scraper's output is not shown to be the production `jobs.csv` source. Until the owner identifies and authorizes a producer, an existing `jobs.csv` is only an input artifact with unverified provenance. Do not imply that it represents a fresh or complete live collection.

**Owner approval required:** authoritative producer, permitted manual/import sources, whether raw-byte identity is the required source identity, and whether source metadata (producer, query/scope, collection time) is mandatory. No source should become production-authoritative by convention or filename alone.

## 3. Occurrence accounting

One occurrence is one parsed data record at a 1-based ordinal in the exact source snapshot. Duplicate rows are separate occurrences. A stable occurrence reference should be derived from the source fingerprint plus ordinal; it is for accounting and traceability, not a security identity.

Every occurrence must have exactly one terminal disposition:

| Disposition | Meaning | Required accounting |
|---|---|---|
| `PROCESSED` | The stage completed the required work for this occurrence and emitted its required row/result. A quality warning such as an inadequate description does not by itself mean extraction failed. | Count and output reference; any quality classification. |
| `INTENTIONAL_SKIP` | An owner-approved policy rule explicitly makes the occurrence ineligible for this stage. | Count, stable reason code, and policy/rule reference. |
| `FAILED` | Required work was attempted or required source data was invalid/unavailable. | Count, stable error code, occurrence reference, and diagnostic. |

Reconciliation is mandatory: `source_record_count = processed_count + intentional_skip_count + failed_count`; counts are nonnegative integers and occurrence references are unique within a run. Output row counts are reported separately because skips and failures do not necessarily emit normal output rows. Missing accounting is not equivalent to a skip.

### Proposed record rules; owner approval required

- **Missing job link:** classify as `FAILED` by default because the record cannot be fetched or reliably joined. It may become `INTENTIONAL_SKIP` only under an explicit approved source-validation rule with a reason code. Never silently `continue` without accounting.
- **Duplicate records:** preserve each occurrence and process it by default. If approved deduplication is needed, mark each suppressed duplicate as `INTENTIONAL_SKIP(DUPLICATE)` and reference the retained occurrence. Do not silently deduplicate or conflate occurrences.
- **Blank description:** if extraction completed successfully but the source page has no usable description, count the occurrence as `PROCESSED` with a quality state such as `DESCRIPTION_MISSING`; analyzer should emit `INSUFFICIENT_DATA` and make it ineligible. A navigation/extraction exception is `FAILED`, even if a blank row is retained for diagnostics. Owner must decide whether a missing description is a successful low-quality result or an extraction failure for particular source conditions.
- **Validation rejection:** use `INTENTIONAL_SKIP` only for an owner-approved eligibility rule. Malformed required fields or an unclassified rejection are `FAILED`.
- **Per-record extraction exception:** `FAILED` with diagnostic; retain useful successful outputs for other occurrences only as `PARTIAL` under the status rules below.
- **All skipped:** a nonempty source with all records intentionally skipped is not `EMPTY`. Recommend `COMPLETE` only when the skip policy is explicit, every occurrence is reconciled, and required stage artifacts include the accounting/diagnostics ledger. The existing helper can represent `COMPLETE` with zero processed records; production semantics must explicitly decide whether that is allowed.

## 4. Status lifecycle and selection

`IN_PROGRESS` is nonterminal. It records an attempt that has begun but has not completed validation and publication. It is never selectable. A process interruption leaves the run unselectable; recovery must not infer completion from files left behind.

| Status | Proposed exact condition | Candidate selection |
|---|---|---|
| `COMPLETE` | Valid nonempty source; all source occurrences reconciled; zero failed occurrences; all skips follow approved rules; all required stage outputs and diagnostics are validated and bound to this run. It may have processed occurrences or be all-skipped only if owner-approved. | Eligible for downstream evaluation only after the selected pointer, manifest, artifact bytes, and upstream binding validate. Actual candidate-level filters still apply. |
| `EMPTY` | Source is valid and has zero data records; accounting is all zero; no data rows/results. This is distinct from a nonempty all-skipped source. | Selects zero candidates. Never fall back to an older generation or legacy CSV. |
| `PARTIAL` | Nonempty input; at least one occurrence processed and at least one failed; accounting reconciles; valid outputs/diagnostics clearly identify successes and failures. | Retain for diagnostics only. Never eligible for automatic application selection. |
| `FAILED` | Source missing/malformed, stage-level transform/serialization/validation failure, no useful processed records when required work failed, or publication/consistency validation failed. | Never selectable. Do not expose incomplete outputs as current. |
| `IN_PROGRESS` | Work started without validated terminal result. | Never selectable. |

Recommend that all-required-extractions-failed is `FAILED`, not `PARTIAL`, because it yields no useful processed result. Recommend that a valid zero-record source is `EMPTY`, not `FAILED`. These and all-skipped behavior require owner approval.

Stage-level failures (including inability to write or validate any required output) make the stage `FAILED`; a process crash before a terminal record leaves `IN_PROGRESS`. If CSV replacement succeeds but diagnostics replacement fails, that attempt is unselectable and the prior selected complete generation remains unchanged. Never treat a pair with mismatched run IDs or hashes as complete.

## 5. Details-to-analysis binding

Each analyzer run must name the exact `job_details` generation it consumed, including that generation's run ID, terminal status, manifest fingerprint, and the details artifact fingerprint (SHA-256 and byte size). The analyzer must read and parse the exact bytes it validates. It must reject absent, malformed, incomplete, `PARTIAL`, `FAILED`, or `IN_PROGRESS` details generations. `EMPTY` details may produce only `EMPTY` analysis; `COMPLETE` details may produce `COMPLETE`, `PARTIAL`, or `FAILED` analysis according to analyzer accounting.

For `COMPLETE` analysis, every input occurrence must be represented by either an analysis result or an approved intentional skip, and transformation must complete. An inadequate description is an accounted ineligible result, not silent omission. Any failed required transformation makes analysis `PARTIAL` when useful results remain, otherwise `FAILED`. Neither partial output nor a stale fixed-path file is candidate-selectable.

The consumer (`easy_apply`) must validate the pointer and both manifests/artifacts, verify the selected analysis manifest names the exact selected details generation, verify fingerprints/byte sizes, then parse those verified bytes. If any metadata is absent or inconsistent, it returns no candidates. Current mtime/identity checks may remain temporary diagnostics, but cannot substitute for generation binding.

## 6. Pointer, failed publication, and rollback

The helper currently validates pointer-shaped data; it does not publish a pointer, coordinate writers, authenticate rollback authority, or establish atomicity/durability. Its rollback actor/reference/reason fields are strings, not proof of authorization. A production design must not treat those fields alone as authorization.

**Proposed selection behavior:** keep attempt state (`latest_attempt`) distinct from selected state (`selected_generation_id`/mode). A successful validated `COMPLETE` attempt may select `CURRENT`; a validated `EMPTY` attempt may select `EMPTY`, explicitly meaning zero candidates. `PARTIAL`, `FAILED`, or `IN_PROGRESS` attempts do not select their output. If a prior complete generation is to be selected after a later failure, it remains selected only if policy explicitly permits the previous selection to remain current; otherwise selection becomes `NONE` until an explicit rollback event. The owner must choose this policy. Under neither policy may the failed attempt become selectable.

Before implementation, define a durable publication protocol for every supported storage provider. At minimum: write isolated generation artifacts; validate exact bytes and all cross-references; publish a terminal manifest; then publish the selection pointer last. If pointer publication fails, leave the new generation unselected. If the pointer is missing, malformed, stale, or contradictory, fail closed; do not scan for a plausible generation or fall back to fixed CSV paths. A crash/atomicity guarantee must be demonstrated on each supported filesystem/provider, not inferred from `os.replace` or successful unit tests.

Rollback must be explicit, auditable, separately authorized, and validated against the retained prior `COMPLETE` generation. Record actor, time, reason, prior and target run IDs, and source-identity relationship. Recommend permitting rollback only when the prior generation has validated artifacts and matches the current source fingerprint; whether a changed source may be rolled back to stale results is an owner decision and should default to reject.

Retention/cleanup must never remove the selected generation or the last approved rollback generation. Cleanup is a separate authorized operation with a documented retention period/count and must not race writers/readers. No cleanup behavior is implemented by the helper.

## 7. Tracker continuity

`application_tracker.csv` and `application_history.csv` are persistent application-state records, not generated stage outputs. Do not replace, reset, or scope them to a pipeline generation. Join current candidates to tracker/history by a stable normalized job identity (prefer canonical platform job ID; URL normalization is a fallback), not row position or generation ID. Jobs absent from a new generation remain in tracker/history but are not offered as current candidates. Preserve application status/history through empty, failed, and partial pipeline runs.

Owner approval is required for identity collisions, duplicate job IDs/URLs, URL changes, merge behavior, and conflicts between tracker and application history. Until resolved, ambiguous identities must not be automatically merged or submitted.

## 8. Legacy CSV migration and compatibility

- Existing fixed-path CSV/diagnostics without a valid manifest remain preserved and classified `LEGACY_UNVERIFIED`. Do not adopt them as `COMPLETE` based only on timestamps, row counts, or matching job identities.
- Before enforcement, generate a new isolated generation from a validated source snapshot; legacy files remain untouched. No automatic migration may relabel old bytes as a new run.
- During staged migration, do not let a consumer silently mix generation-backed details with fixed-path analysis or vice versa. Each consumer uses one declared mode; generation enforcement never falls back to legacy paths.
- Under enforcement, missing/invalid manifests, mismatched output hashes, different run IDs, partial/failed/in-progress states, stale/corrupt pointers, or legacy-only outputs yield no candidates.
- External consumers are unknown from repository inspection. Inventory and test them before retiring fixed paths. Keep fixed outputs as compatibility exports only if their semantics are explicit and they cannot be mistaken for the selected generation.

Recommended migration order (each step separately reviewed): (1) approve this policy and the environment/security contract; (2) implement and test isolated generation storage; (3) add the details generation writer and occurrence ledger; (4) add analyzer exact-input binding; (5) add fail-closed candidate consumer enforcement; (6) preserve tracker/history continuity; (7) inventory and migrate external/fixed-path consumers; (8) separately approve cleanup, rollback, and any collection/publication changes. Do not begin a later step until its dependencies and tests pass.

## 10. Integration gate

**Production integration recommendation: NO-GO.** The helper is a standalone validation foundation, not an integrated recovery/publication system. Owner policy decisions above are open; source producer authority and external compatibility are unknown; pointer publication, locking, crash recovery, and tracker bridging are not implemented; and the separate Windows filesystem security rejection remains in force. No production writer/consumer changes are authorized by this proposal. Reconsider only after owner approval, a written specialist decision, separately authorized Windows acceptance tests with retained evidence for each supported configuration, and a new explicit implementation authorization. Collection publication and application submission remain disabled independently of this pipeline contract.
